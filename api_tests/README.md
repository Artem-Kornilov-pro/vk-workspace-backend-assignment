# api_tests

Часть 3: API-тесты службы `ghreport` по принципу чёрного ящика. Служба запускается отдельным процессом, проверяются отчёт, журнал `--trace`, кэш и коды возврата. Python ≥ 3.10, pytest ≥ 7, других зависимостей нет.

## Запуск

```sh
python3 -m venv .venv && .venv/bin/pip install -r api_tests/requirements.txt
(cd service && go build -o /tmp/ghreport ./cmd/ghreport)

# только встроенный мок-сервер
GHREPORT_BIN=/tmp/ghreport .venv/bin/pytest api_tests -q

# плюс контрактный сервер
GHREPORT_BIN=/tmp/ghreport GITHUB_API_BASE_URL=https://api.github.com GITHUB_TOKEN=... \
GHREPORT_TEST_REPO=cli/cli .venv/bin/pytest api_tests -q
```

| Переменная | Назначение |
|---|---|
| `GHREPORT_BIN` | абсолютный путь к собранной службе, обязательна |
| `GITHUB_API_BASE_URL` | контрактный сервер; если задан, все тесты с данными выполняются и против него |
| `GITHUB_TOKEN` | токен для этого сервера, необязателен (для api.github.com без токена лимит — 60 запросов в час, набору этого не хватит) |
| `GHREPORT_TEST_REPO` | репозиторий с данными на этом сервере, по умолчанию `cli/cli`; для мок-сервера, запущенного отдельно, — `mock/main` |

Время прогона: около 35 с только с мок-сервером, около 2 минут вместе с api.github.com.

## Как устроен набор

Проверяющий может запустить набор против **сломанного сервера** или **сломанной службы**, и в обоих случаях тесты должны падать. Поэтому тесты не доверяют ни одной из сторон:

- **Тесты с данными** (фикстура `server`) параметризованы двумя серверами: `mock` — встроенный мок-сервер, `external` — `GITHUB_API_BASE_URL`, если он задан. Тест сам обходит сервер по контракту (`server_client.py`: urllib, переход по `Link`), проверяет его ответы и вычисляет ожидаемый отчёт по правилам службы, а затем сравнивает с отчётом `ghreport` поле в поле. Состав выдачи, число страниц и значения полей заранее не известны — всё берётся с сервера.
- **Контракт самого сервера** проверяется отдельно (`test_server_contract.py`): ответы — JSON-массивы с корректными `number` и `created_at`, PR помечены `pull_request`, сортировка по `created_at` по возрастанию, 304 только на совпавший `If-None-Match`, а обход страницами по 100 и по 30 даёт одну и ту же последовательность — так ловятся пропуски элементов на границах страниц и отсутствие `Link` при наличии следующей страницы.
- **Сценарии, которые нельзя гарантировать на чужом сервере** — 429/403 с паузой, 401, 5xx, обрыв соединения, битый JSON — идут против своего мок-сервера на каждый тест (фикстура `mock`). Мок записывает запросы службы, поэтому проверяются и заголовки, адреса, последовательность запросов и переход по `Link`.
- Тесты проверяют только то, что задано контрактом. Например, `--limit` подбирается так, чтобы не разрезать группу issue с одинаковым `created_at` (внутри неё контракт допускает разный выбор), а мок отдаёт `Link` и в ответе 304 — чтобы корректная служба, которая не хранит `Link` в кэше, не падала ложно.

### Файлы

| Файл | Содержимое |
|---|---|
| `conftest.py` | `run_ghreport(server, *args, ...)` — запуск службы процессом; `report_of(server, repos, *args, expect_code=...)` — запуск, проверка кода, схемы отчёта и журнала; фикстуры `server`, `mock` |
| `mock_server.py` | мок-сервер контракта (`http.server` в потоке), запускается и отдельно |
| `server_client.py` | прямые запросы к серверу, обход по `Link`, ожидаемый отчёт |
| `checks.py` | проверки схемы отчёта и журнала, применяются к каждому запуску |
| `test_*.py` | тесты (см. ниже) |

### Покрытие

| № | Требование | Тесты |
|---|---|---|
| 1 | пагинация и `--limit`: ровно limit, без повторов `number` | `test_pagination.py`: limit на несколько страниц, limit 1/7/99/100/101, повторы между страницами, адреса страниц только из `Link`, остановка после набора limit, limit больше числа issue |
| 2 | PR нет в отчёте | `test_pull_requests.py`: ни номеров PR, ни `/pull/` в url, PR не занимают места issue; репозиторий только из PR |
| 3 | `--since` | `test_since.py`: дата из середины данных, issue ровно в полночь UTC, дата в будущем, параметр API `since` не используется |
| 4 | кэш | `test_cache.py`: второй запуск — все строки журнала `from_cache: true` и 304, отчёт совпадает; `If-None-Match` только при наличии кэша; изменившиеся данные перечитываются и кэш обновляется; токена в кэше нет |
| 5 | 429 + `retry-after` | `test_rate_limit_and_retries.py`: пауза не меньше `retry-after` и успех, 403 с `x-ratelimit-remaining: 0` до `x-ratelimit-reset`, лимит посреди пагинации; повторы 5xx с паузами 1, 2, 4 с, исчерпание повторов → `request_failed`, обрыв соединения |
| 6 | 401 → код 3; 404 по одному репозиторию → код 1 | `test_errors.py`: неверный и отсутствующий токен, 401 после успешного репозитория, 404 одного из репозиториев, один или все репозитории 404 → `all_failed`, битый JSON → `invalid_response`, 12 вариантов некорректных аргументов → код 2, пустой stdout, ни одного запроса |
| 7 | схема отчёта | `checks.check_report` для каждого отчёта: точный набор полей, типы, `generated_at` в UTC, `count == len(issues)`, сортировка, уникальность; `test_report_schema.py`: значения полей против данных сервера, текущее `generated_at`, порядок и дубликаты `--repos`, одинаковый `created_at`, несколько репозиториев, `--out` |
| 8 | журнал | `checks.check_trace` для каждого журнала: точный набор полей и типы; `test_trace.py`: первый запрос по контракту, одна строка на каждый запрос, токена и `Authorization` нет ни в журнале, ни в stdout/stderr, ни в кэше |
| — | запросы службы | `test_requests.py`: заголовки, Bearer-токен и его отсутствие, адрес первой страницы, переход только по `Link`, последовательные запросы, завершающий слеш в `GITHUB_API_BASE_URL` |

### Качество

- **Детерминированность.** В тестах нет `sleep`: паузы службы измеряются по времени запросов, которое записывает мок-сервер, а сам мок следит, чтобы повтор после 429 не пришёл раньше срока. Данные мок-сервера генерируются с фиксированным seed. Все ожидания ограничены таймаутом запуска службы (120 с).
- **Независимость от порядка.** У теста свой каталог кэша в `tmp_path`, у сценариев ошибок — свой экземпляр мок-сервера. Общий на сессию только обход сервера для ожидаемых данных — он лишь читает.
- **Запросы самих тестов** к мок-серверу (по `User-Agent: ghreport-api-tests/...`) не попадают в его журнал и не расходуют сценарии ошибок, предназначенные для службы.

## Мок-сервер отдельно

```sh
python api_tests/mock_server.py --port 8000 [--fault NAME ...] [--token TOKEN]
```

Репозитории: `mock/main` (260 элементов, 3 страницы, PR, повторы на границах страниц, одинаковые `created_at`), `mock/small`, `mock/second`, `mock/empty`, `mock/only-prs`. Следующие страницы — непрозрачные курсоры `/_cursor/...`, первая страница — только по точному адресу контракта (лишние параметры → 400).

## Самопроверка: набор падает на сломанном сервере и сломанной службе

**Сломанный сервер** — мок-сервер с поломкой как `GITHUB_API_BASE_URL` (`GHREPORT_TEST_REPO=mock/main`), падающие тесты `[external]`; на исправном сервере падений нет:

| Поломка (`--fault`) | Что не так | Упало тестов |
|---|---|---|
| `skip_item` | на границе страниц пропущен элемент | 1 (`test_page_size_does_not_change_the_items`) |
| `unmarked_pr` | PR без ключа `pull_request` | 18 |
| `always_304` | 304 на запрос без `If-None-Match` | 21 |
| `broken_json` | битый JSON на второй странице | 13 |
| `sort_desc` | сортировка по убыванию | 1 (`test_items_are_sorted_by_created_at_ascending`) |
| `no_link` | нет `Link` при наличии следующей страницы | 1 (`test_page_size_does_not_change_the_items`) |
