## 1. Часть 1 — msgfmt (C++17)

Markdown-подмножество → `{"text": ..., "ranges": [...]}`, позиции в **кодовых единицах UTF-16**.

### Сборка / требования
- `cmake -S msgfmt -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build && ctest --test-dir build`
- Исполняемая цель `msgfmt`, тесты зарегистрированы в CTest.
- Только стандартная библиотека. Без предупреждений с `-Wall -Wextra`. Чисто под `-fsanitize=address,undefined`.

### Вход
- Байты UTF-8. Невалидный UTF-8 — **единственная** ошибка.
- Без нормализации Unicode. `\n` и управляющие символы — обычный текст.

### Термины
- Диапазон = (style, offset, length, url); style ∈ {bold, italic, code, link}; url = "" для всех, кроме link.
- BMP-символ = 1 единица UTF-16, вне BMP (эмодзи) = 2 (суррогатная пара).
- Служебные символы: `*  _  `` ` ``  [  ]  (  )  \`

### Правила разбора (приоритет над примерами)
1. Однопроходно, слева направо; диапазоны строятся по ходу.
2. Открывающие: `**` bold, `_` italic, `` ` `` code, `[` link.
3. Открывающий `_` — только на границе слова: перед ним начало текста или не буква/цифра; после — непробельный. Закрывающий `_` — если за ним конец текста или не буква/цифра. (`a_b_c` — без курсива.)
4. После `**`, `` ` ``, `[` должен идти непробельный символ (`2 ** 3`, `** 3` — литералы).
5. Закрывающий — ближайший подходящий, перед которым непробельный символ.
6. Нет закрывающего / неполная конструкция → символы выводятся как обычный текст.
7. Содержимое code — как есть: разметка и экранирование внутри не действуют.
8. Ссылка `[текст](url)`: текст непустой, без `]`; url непустой, без пробельных символов и без `)`. Иначе — литералы (`[текст]()` — литералы).
9. `\` перед служебным символом → символ становится обычным; перед любым другим — `\` сохраняется.
10. Вложенность разных стилей разрешена. Маркер того же стиля внутри уже открытого — просто текст.
11. Пустой вход → пустой текст, пустой список.
12. Сортировка: offset ↑; при равных — length ↓; при полном совпадении — раньше открытый стиль первым. Частичных пересечений не бывает.

### CLI
- `msgfmt` (без аргументов): stdin → JSON в stdout. Код 0.
- `msgfmt escape`: stdin → текст, каждый служебный символ предварён `\`. (`2 * 3` → `2 \* 3`)
- Невалидный UTF-8 (обе команды): stdout `{"error": "invalid_utf8"}`, код **2**.
- JSON: порядок полей не важен, **лишних полей нет**, вывод детерминирован. Корректное экранирование строк в JSON (кавычки, `\`, управляющие символы).

### Контрольные примеры (Приложение А)

| № | Вход | Текст | Диапазоны |
|---|------|-------|-----------|
| 1 | `**важно**` | `важно` | bold(0,5) |
| 2 | `Привет, **мир**!` | `Привет, мир!` | bold(8,3) |
| 3 | `_курсив_` | `курсив` | italic(0,6) |
| 4 | `a_b_c` | `a_b_c` | — |
| 5 | `**не закрыто` | `**не закрыто` | — |
| 6 | `2 \* 3` | `2 * 3` | — |
| 7 | `` `чат * список` `` | `чат * список` | code(0,12) |
| 8 | `[документация](https://docs.github.com)` | `документация` | link(0,12,https://docs.github.com) |
| 9 | `**жирный _и_ курсив**` | `жирный и курсив` | bold(0,15); italic(7,1) |
| 10 | `💅 **ок**` | `💅 ок` | bold(3,2) |
| 11 | `**💅 ок**` | `💅 ок` | bold(0,5) |
| 12 | `[текст]()` | `[текст]()` | — |
| 13 | `\\` | `\` | — |
| 14 | (пустой вход) | (пустая строка) | — |
| 15 | `_ e_` | `_ e_` | — |

Заметки: в №9 на картинке подчёркивания смазаны спеллчекером, но italic(7,1) = слово «и» → вход `_и_`. В №10–11 эмодзи = 2 единицы.

### Артефакты

## 2. Часть 2 — ghreport (Go + Docker)

Сводка по открытым issue репозиториев GitHub.

### CLI

```
ghreport --repos <owner/repo[,owner/repo...]>
         [--limit <N>] [--since <YYYY-MM-DD>]
         [--out <file|->] [--trace <file>] [--cache-dir <dir>]
```

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--repos` | строка | обязателен | через запятую, `owner/repo`; дубликаты удаляются с сохранением первого вхождения |
| `--limit` | целое | 100 | максимум issue на репозиторий, ≥ 1 |
| `--since` | дата | — | issue, созданные не раньше даты (00:00:00 UTC) |
| `--out` | путь | `-` | файл отчёта; `-` = stdout |
| `--trace` | путь | — | журнал JSONL; без флага не ведётся |
| `--cache-dir` | путь | `./.ghreport-cache` | создаётся автоматически |

Некорректные аргументы → сообщение в stderr, stdout пуст, код 2.
Пример: `ghreport: --limit должен быть целым числом, не меньшим единицы`

### Переменные окружения (не вшивать в код и образ)
- `GITHUB_TOKEN` — необязательный, `Authorization: Bearer <token>`.
- `GITHUB_API_BASE_URL` — по умолчанию `https://api.github.com`; **завершающий слеш допускается** (нормализовать). Если задан — ходить именно туда, в т. ч. в контейнере.

### Запрос
- Только `GET {base}/repos/{owner}/{repo}/issues?state=open&sort=created&direction=asc&per_page=100`
- Заголовки: `Accept: application/vnd.github+json`, `User-Agent` (осмысленный, описать в README), `X-GitHub-Api-Version: 2026-03-10`, `Authorization: Bearer` при наличии токена.
- Все запросы **последовательно**.
- Редиректы 301/302/307 — по документации GitHub.
- Таймаут одного запроса ≤ 30 с.

### Пагинация
- Следующая страница — **только** из `Link: <...>; rel="next"`; вручную URL не строить.
- Цикл: запросить → взять подходящие → если набрано limit или нет `next` — стоп → иначе по `next`.
- Порядок: created_at ↑, затем number ↑.

### Фильтрация и дедупликация
- Исключить PR: наличие ключа `pull_request`.
- `--since`: исключить created_at < начала даты (UTC). Фильтровать самим, параметр API `since` НЕ использовать (он по updated_at).
- Одинаковый `number` — один раз (повторы между страницами).

### Кэш (`--cache-dir`)
- Для каждого URL хранить ETag и тело успешного ответа.
- Повторный запрос того же URL → `If-None-Match`.
- 304 → тело из кэша, в журнале `from_cache: true`.
- 200 → обновить кэш, `from_cache: false`.
- Переживает перезапуски, **не содержит токен**. Формат описать в README.

### Лимиты и повторы
- Исчерпание лимита: код 403 или 429 **и** (в теле сказано про rate limit, или есть `retry-after`, или `x-ratelimit-remaining: 0`).
- Пауза: `retry-after` → иначе до `x-ratelimit-reset` (epoch UTC) → иначе ≥ 60 с.
- Сетевые ошибки и 5xx: до 3 повторов с задержками 1, 2, 4 с.
- После исчерпания повторов — код ошибки у репозитория, переход к следующему.

### Коды ошибок репозитория
`not_found` (404), `rate_limited`, `request_failed` (сеть/5xx после повторов), `invalid_response` (не JSON).

### Коды возврата

| Код | Ситуация | Вывод |
|---|---|---|
| 0 | все репо успешно | отчёт |
| 1 | часть репо с ошибкой | отчёт, у проблемных заполнен `error` |
| 2 | некорректные аргументы | сообщение в stderr |
| 3 | 401 **или** все репо с ошибками | `{"error": "unauthorized"}` или `{"error": "all_failed"}` в stdout |

Следствие: один репо с 404 → код 3 (`all_failed`), а не 1.

### Формат отчёта

```json
{
  "generated_at": "<UTC RFC3339>",
  "repos": [
    {
      "repo": "owner/repo",
      "error": null,
      "count": 2,
      "issues": [
        {"number": 1, "title": "...", "author": "octocat", "labels": ["bug"],
         "created_at": "2026-01-05T10:00:00Z", "url": "https://github.com/cli/cli/issues/1"}
      ]
    },
    {"repo": "example/missing", "error": "not_found", "count": 0, "issues": []}
  ]
}
```

- Порядок репо — как в `--repos` (после удаления дубликатов).
- issues: created_at ↑, затем number ↑; `count == len(issues)`.

| Поле отчёта | Источник |
|---|---|
| number | number |
| title | title |
| author | user.login |
| labels | labels[].name, в порядке ответа |
| created_at | created_at (как в ответе API) |
| url | html_url |
| count | вычисляется |
| generated_at | текущее время UTC |

### Журнал `--trace` (JSON Lines)
Одна строка на **каждую попытку** HTTP-запроса, по порядку:
`ts` (RFC3339 UTC), `method`, `url` (полный), `status` (0 если ответа нет), `attempt` (с 1), `from_cache`, `error` (null или кратко: `timeout`, `network`).
Authorization не писать.

```json
{"ts":"2026-10-14T09:00:01Z","method":"GET","url":"https://api.github.com/repos/cli/cli/issues?per_page=100","status":200,"attempt":1,"from_cache":false,"error":null}
```

### stdout / stderr
- stdout — только отчёт или фатальный JSON. Диагностика — в stderr.
- Токен — нигде (stdout, stderr, журнал, кэш).

### Docker
- `service/Dockerfile`, `service/.dockerignore`.
- `docker build -t ghreport service/`
- `docker run --rm -e GITHUB_TOKEN=... ghreport --repos cli/cli --limit 20 --out -`
- `-e GITHUB_API_BASE_URL=...` для другого сервера.
- `USER` непривилегированный, секретов в образе нет, от файлов хоста не зависит.
- План: multi-stage (golang → distroless/static или alpine), `CGO_ENABLED=0`.

### Артефакты
`go test ./...` проходит; `gofmt -l` и `go vet ./...` чисто. README: запуск, архитектура, формат кэша, обработка лимитов, примеры вывода, переменные окружения.

## 3. Часть 3 — api_tests (pytest)

Чёрный ящик: запускаем `ghreport` процессом, проверяем отчёт, журнал, коды возврата.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `GHREPORT_BIN` | абсолютный путь к собранной службе |
| `GITHUB_API_BASE_URL` | базовый адрес сервера, совместимого с контрактом части 2 |
| `GITHUB_TOKEN` | необязательный |

### Ограничения
- Работать с **любым** контрактным сервером: состав выдачи, число страниц, значения полей заранее неизвестны.
- В сеть — только `GITHUB_API_BASE_URL`, только чтение.
- Каждый тест — свой временный каталог кэша (`tmp_path`).

### Покрытие (обязательно)
1. Пагинация + `--limit`: при нескольких страницах ровно limit элементов, без повторов number.
2. PR отсутствуют в отчёте.
3. `--since`: только issue не раньше даты.
4. Кэш: повторный запуск с тем же кэшем → `from_cache: true` в журнале, отчёт совпадает с первым.
5. 429 + `retry-after` → пауза и успешное завершение.
6. 401 → код 3; 404 по одному из репо → код 1 и `error` у этого репо.
7. Схема отчёта: обязательные поля, типы, сортировка.
8. Журнал: набор полей, нет Authorization.

### Качество
- Детерминированность: без произвольных sleep; ожидания ограничены таймаутом.
- Независимость от порядка.
- Полный прогон ≤ 10 минут.
- **Ловить нарушения контракта**, а не только happy path. Примеры: пропуск элемента при пагинации; PR без признака `pull_request`; 304 на запрос без If-None-Match; битый JSON; неверное направление сортировки; нет Link при наличии следующей страницы.

### Стратегия (решено)
- Проверяющие, скорее всего, запустят набор против **сломанного** сервера или **сломанной** службы и будут ждать падения тестов.
- Поэтому тесты не только проверяют форму отчёта, но и **сами ходят в `GITHUB_API_BASE_URL`** (urllib) и сверяют отчёт с реальными данными сервера (пагинация по Link, наличие PR, сортировка, 304 только при If-None-Match и т. д.).
- Для сценариев, которые нельзя гарантировать на чужом сервере (429/retry-after, 401, 404), — собственный мок-сервер в pytest-фикстуре (`http.server` в потоке).
- Имена репозиториев — через переменные окружения с дефолтами (например, `stub/alpha`), описать в README.
- `conftest.py` содержит `run_ghreport(...)` и `report_of(...)`; тесты не дублируют работу с процессами.

### Артефакты
`api_tests/` + `requirements.txt` (pytest) + README: `pytest api_tests -q` и список переменных.

## 4. Решения, которые надо зафиксировать в README

- **Редиректы**: 301 → идти по `Location` (постоянный); 302/307 → по `Location` для этого запроса. Не передавать Authorization на другой хост.
- **Кэш**: файл на URL, имя = sha256(URL), внутри JSON `{url, etag, body}`; URL без токена.
- **Лимит повторов при rate limit**: в ТЗ не задан — ограничить (например, 3 ожидания), затем `rate_limited`. Возможно, ограничить максимальную паузу.
- **401 посреди работы**: сразу фатально, код 3, `{"error":"unauthorized"}`.
- **User-Agent**: например `ghreport/1.0 (+vk-workspace-backend-assignment)`.
- **msgfmt**: что считать «буквой или цифрой» для `_` (ASCII + Unicode-буквы, например кириллица) и «пробельным символом» — описать.
